# Vending Machine FSM — Design Notes

## Spec
Item costs 10 cents, accepts only 5-cent coins (`coin_in`, one per event). Once 2 coins have
been inserted, `dispense` fires for one cycle, then the machine resets to waiting.

## States (2 states only)
- `s0` — 0 cents inserted so far (idle/reset state)
- `s1` — 5 cents inserted so far (waiting for the second coin; patiently stays here indefinitely
  if no second coin arrives)

## Transition table

| Current State | coin_in | Next State | dispense |
|---|---|---|---|
| s0 | 0 | s0 | 0 |
| s0 | 1 | s1 | 0 |
| s1 | 0 | s1 | 0 |
| s1 | 1 | s0 | 1 |

Only 2 states needed — no dedicated "just dispensed" state, since the Mealy output (`dispense`)
can fire as part of the s1->s0 transition itself, without needing a separate state to represent it
(same principle confirmed from the sequence detector: Mealy outputs don't need their own state).

## A real hardware bug found and fixed: input pulse width

Initial design checked `coin_in` directly. Testing revealed: if `coin_in` stays HIGH for multiple
clock cycles (which is realistic — any physical sensor/button signal is "held" for many cycles
relative to a fast clock, not a perfectly clean single-cycle pulse), the machine would
incorrectly dispense after only ONE coin, since the combinational condition
`state==s1 && coin_in==1` stays true for as long as the raw signal is held high.

**Fix: edge detection.** Added a 1-cycle-delayed copy of `coin_in` (`coin_in_prev`, via a simple
D-flip-flop pattern), then derived `coin_pulse = coin_in & ~coin_in_prev` — true only for exactly
one cycle, on the genuine rising edge, regardless of how long the raw input stays high
afterward. All state-transition and output logic then uses `coin_pulse` instead of raw `coin_in`.

This is a general, reusable technique for any FSM design that reacts to a physical/external
event signal (buttons, sensors) rather than a signal generated by another clean synchronous
circuit.

## Verification — including a "testbench bug, not design bug" lesson

Compiled with Icarus Verilog and tested against several scenarios:
- Coin held high for multiple cycles -> confirmed NO spurious dispense (bug fixed)
- Two genuinely separate clean coin pulses -> confirmed correct dispense on the second
- Held-high coin, released, then one more clean pulse -> confirmed this correctly DOES dispense,
  since the machine correctly remembers the first 5 cents was already registered

One test initially appeared to fail (a "fresh" 2-coin scenario immediately following a held-high
scenario). Signal-level tracing revealed the actual cause: the **testbench** forgot to reset
between independent scenarios, so leftover state (1 coin already registered) correctly carried
into the next scenario and combined with the "new" coin to trigger a real, correct dispense
one coin sooner than the test expected. The design was correct; the test needed a reset between
independent scenarios. This is a genuine, common verification lesson: a failing test does not
automatically mean the design is wrong — determining whether the design or the test itself has
the bug is itself a core verification skill.
